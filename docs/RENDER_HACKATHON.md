## Optional second free resource: public synthetic store

For a stronger Render demo and a store reachable by Kernel, deploy the public repository as a **Free Web Service** named `rewardloop-store`, using `npm ci && npm run build` and `npm start`. Use the same database's **internal** URL because this service runs on Render in the database's region. Give the service the required `BETTER_AUTH_SECRET` and 43-character base64url `DATA_ENCRYPTION_KEY` in Render secret fields, while leaving PayPal, Channel3, and Kernel keys absent from this store process. Configure `APP_ORIGIN` and `BETTER_AUTH_URL` as the local app's exact `http://localhost:3000` origin and `MOCK_STORE_ORIGIN` as this service's assigned `https://...onrender.com` origin, then redeploy after the hostname is known. Set `ALLOW_FIXTURE_PROVIDERS=false` and retain the fixed PayPal Sandbox mode values. Its health-check path should be `/store`, because the app's host-isolation proxy deliberately returns 404 for `/api/healthz` on the store hostname.

The current proxy intends to serve only synthetic store routes on its configured hostname, but this public deployment needs a store-only service guard and a Host-header bypass test before creation; hostname checks alone are not a sufficient public isolation boundary. The app's one-time store code would be created locally and redeemed by the remote store against the shared database. The local worker could then bind that cart and run its locally hosted Qwen reviewer and PayPal Sandbox flow. Verify the actual Host and Origin headers, secure store cookie, cross-host cart binding, and free-service wake behavior in a browser before describing this as working. The Render service must never receive a real retailer credential or place a real order. Its repository deployment must use the same schema version as the migrated database.

## Hosted judge demo after local capture

The app is server rendered and has a polling worker, so a static site cannot host the working flow. A complete public deployment also needs two distinct HTTPS hostnames: one for the main app and one for the controlled synthetic store. The store's exact hostname must be `MOCK_STORE_ORIGIN`; the app hostname must be `APP_ORIGIN` and `BETTER_AUTH_URL`. Kernel's cloud browser can use the store only when that origin is publicly reachable. The Render database URL for Render services should be the **internal** URL in the same region.

Render [offers free web services](https://render.com/docs/free), but free services sleep after 15 minutes of idle traffic, may take about a minute to wake, have ephemeral filesystems, and cannot run a separate free background-worker service or paid-only pre-deploy migrations. The current `render.yaml` describes a separate paid worker and uses `preDeployCommand`, so it is not a free-tier configuration. The locally downloaded Qwen model is excluded from Git and too large for the 512 MB free web-service memory; a hosted worker needs a separately configured and verified hosted reviewer or a materially different model deployment. Do not point the hosted reviewer at `127.0.0.1` expecting to reach the owner's machine.

For a credit-backed paid configuration, the current Blueprint's small paid web, worker, and database plans have published base prices of about **$7 + $7 + $6 = $20/month** before other usage, according to [Render pricing](https://render.com/pricing). That is an estimate, not a checkout quote or authorization. Add a second public store hostname/service or suitable custom domain arrangement, verify reviewer access, confirm the exact resource price and credit coverage, then deploy and run a fresh provider-backed smoke test. Keep public signup disabled and use an isolated synthetic judge account. The hosted app must still call only PayPal Sandbox and the controlled store.
