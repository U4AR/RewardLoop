# Kernel synthetic-cart flow

The in-app **Prepare cart with Kernel** action is available only when `KERNEL_API_KEY` is present and `MOCK_STORE_ORIGIN` is a distinct public HTTPS origin. The configured store must serve this same RewardLoop app at `/store` and `/api/store/*`; a local `127.0.0.1` store works for manual testing but cannot be reached by Kernel. The key belongs in ignored local secrets or a deployment secret, never in source control.

After an owner approves a reward, the app queues one cart-preparation job for that exact purchase intent. The worker checks the active goal and permission, approved primary SKU and variant, synthetic seller and destination, total cap, and absence of any quote, existing cart binding, or payment operation. It issues a new one-time synthetic-store code. The first Kernel browser signs in and saves the approved cart in a named profile; the worker closes it to save the profile. A second, distinct, read-only Kernel browser restores the profile and reads the cart. Both reads must show the exact expected store-session ID, SKU, fictional destination, synthetic-only marker, and disabled checkout/shipment. Only then does the worker bind the cart to the intent through the ordinary owner and permission checks. A verified event records the two session IDs without Live View URLs, cookies, or setup code.

Both browser sessions use Kernel's egress allowlist for only the configured store hostname, with private-host routing disabled. Requests to other hosts are blocked by Kernel's browser network policy. Each session has a finite inactivity timeout, and the worker attempts to delete both browsers and the profile before reporting success. A failed provider response, mismatch, changed permission, or unconfirmed cleanup leaves the cart unbound. The browser job never invokes PayPal or a retailer checkout. The existing PayPal Sandbox purchase gate independently rechecks the current bound cart, quote, goal, permission, amount, and payment state.

This path has mocked tests and a production build, but **has not been tested against a live Kernel account**. A real provider smoke needs an owner-created free Kernel account and API key, a publicly reachable HTTPS controlled-store hostname, and an approved synthetic reward. Kernel browser usage may consume provider credits. The older `scripts/kernel-two-session-probe.ts` remains an explicitly invoked diagnostic and does not make a payment.
