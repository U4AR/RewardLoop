# PayPal Sandbox integration

Checked against PayPal's official API and SDK documentation on 7 October 2026. This build accepts only `https://api-m.sandbox.paypal.com` for server API calls. A Sandbox client ID may load PayPal's official browser SDK from `www.paypal.com`; the client secret and saved payment token stay on the server. All storefront orders are simulated. No retailer receives an order and no real money moves.

## Wallet save contract

The [JavaScript SDK save-without-purchase guide](https://developer.paypal.com/sdk/js/v5/save-without-purchase/paypal/) and [Payment Method Tokens guide](https://developer.paypal.com/api/payment-tokens/save-without-purchase/paypal) define the flow:

1. Server `POST /v1/oauth2/token` with client credentials. Add `response_type=id_token` to get a short-lived user ID token for the human SDK session.
2. The browser SDK receives the Sandbox client ID and fresh `data-user-id-token`. Its `createVaultSetupToken` callback calls our authenticated server, which `POST`s `/v3/vault/setup-tokens` with a stable `PayPal-Request-Id`, `payment_source.paypal.usage_type=MERCHANT`, `customer_type=CONSUMER`, and approved callback URLs. The REST schema describes `usage_pattern=IMMEDIATE` as on-demand, nonrecurring, variable-amount payment; it does not require a charge during setup.
3. The buyer approves in PayPal Sandbox. The SDK's `onApprove({vaultSetupToken})` sends the result to our server. Our server must match it to the originating user and unconsumed setup session before exchanging it via `POST /v3/vault/payment-tokens` with `payment_source.token={id: approvedSetupTokenId, type: "SETUP_TOKEN"}`.
4. Store the resulting payment token ID and PayPal `customer.id` as protected, user-scoped server data. A setup token expires after three days by default; it is not the durable credential. Saving a wallet is separate from approving a specific goal purchase.

The JavaScript guide has conflicting sample prose (`PLATFORM`) and request JSON (`MERCHANT`) plus incomplete example server code. For this single controlled merchant, the [REST setup-token schema](https://developer.paypal.com/api/payment-tokens/v3/setup-tokens-create) defines `MERCHANT` as future transactions directly with one merchant, so that is the adapter's setting. Confirm actual Sandbox behavior before claiming unattended use. PayPal also requires risk data collection for customer-initiated Payment Token transactions; inspect the current [FraudNet guidance](https://developer.paypal.com/limited-release/fraudnet/integrate/) and match `PayPal-Client-Metadata-Id` where applicable. Do not fabricate risk identifiers.

## Delayed purchase contract

Only the deterministic purchase gate may initiate a payment. It checks the current goal/rubric version, active permission, model-reviewed distinct-day qualification, exact owner-bound synthetic store session/cart, quote/listing version and availability, one-purchase invariant, lease, exact reward and synthetic destination, USD all-in cap, and the selected Sandbox approval mode. Synthetic demo SKUs have unlimited units; the gate does not reserve a finite retailer quantity. The code persists the frozen payload and `PayPal-Request-Id` before calling the adapter and repeats a local gate check immediately before a financial POST. Provider reads have bounded deadlines. Fixture evidence cannot qualify a Sandbox payment.

For a genuinely approved saved-wallet mode, after the approved business window opens, [Orders v2 create](https://developer.paypal.com/api/orders/v2/orders-create) uses `POST /v2/checkout/orders` with `intent=CAPTURE`, one `purchase_units` entry with the frozen USD total/reference and configured test merchant payee, and `payment_source.paypal.vault_id` set to the saved token. The adapter requests `Prefer: return=representation`. It does not create a month-long authorization hold. This mode is implemented but not account-verified or enabled by default for new permissions.

PayPal's [saved-wallet example](https://developer.paypal.com/api/payment-tokens/save-without-purchase/paypal) shows a **completed capture already in the create-order response**. Do not automatically call capture after create. Match the order reference, amount, currency, merchant, and completed capture ID. PayPal's example order representation omits `payee` and sometimes order `amount`; in that case the adapter retrieves the capture via [Payments v2 GET capture](https://developer.paypal.com/api/payments/v2/captures-get), which can provide `payee.merchant_id`, amount, and related order ID. Missing or conflicting facts remain `OUTCOME_UNKNOWN`, never success. An `APPROVED` order with no capture can use [Orders v2 capture](https://developer.paypal.com/api/orders/v2/orders-capture) with a **different** persisted request ID after a fresh order GET. Pending and buyer-action states remain visible non-success states.

`PayPal-Request-Id` belongs to one logical mutation and its identical payload. It survives worker retries and restarts; create, capture, setup token, and token exchange each have their own ID. [PayPal idempotency](https://developer.paypal.com/api/rest/reference/idempotency/) is endpoint-specific, and the Vault setup/payment-token references specify a three-hour server retention period. After an ambiguous timeout, reconcile with the known order/capture or the original operation ID within its documented retention; never create a new financial operation merely because a worker retried. Concurrent same-ID requests may cause one to fail. A new operation requires an authoritative no-payment outcome and a new gate decision.

## Fresh buyer-approval route

The implemented fallback uses standard PayPal Sandbox Checkout after the model-reviewed goal qualifies. A user must have linked the exact synthetic store cart to the active reward on the app origin. The server freezes the all-in quote and stable create-operation ID, checks the current permission and time window, creates a Sandbox order, and returns that order ID to the official PayPal button for a **new buyer approval for this purchase**. Its `onApprove` callback passes the order ID to the authenticated server. The server verifies that the order belongs to the same user and intent, checks the provider's approval and frozen amount/merchant context, repeats the local gate, and starts a separately identified capture operation. A pending or uncertain result is shown as such; it is not a receipt.

If an existing Sandbox order's quote, cart, or window changes, the order ID is preserved and the intent is parked for review instead of silently opening another order. This route is locally tested with provider test doubles, **not** with the project Sandbox account. It is a fresh human approval flow, not an unattended delayed charge.

## Webhooks

When an HTTPS callback is available, register a webhook on the same Sandbox REST app. The [current event list](https://developer.paypal.com/api/rest/webhooks/event-names/) includes `PAYMENT.CAPTURE.COMPLETED`, `PAYMENT.CAPTURE.PENDING`, `PAYMENT.CAPTURE.DECLINED`, `VAULT.PAYMENT-TOKEN.DELETED`, and `VAULT.PAYMENT-TOKEN.DELETION-INITIATED`; subscribe to the supported events relevant to this app. Use [PayPal's verification endpoint](https://developer.paypal.com/api/webhooks/v1/verify-webhook-signature-post) with the original event, transmitted signature headers, and the configured webhook ID; accept only `verification_status=SUCCESS`. Deduplicate event IDs, then match environment, known order, merchant, amount, currency, and user before reconciling state. The simulator cannot prove a real Sandbox payment.
